# Безопасность Petrolero

## Что защищено на этапе локальной разработки

- Авторизация Better Auth, изолированные сессии и 2FA (TOTP с резервными кодами).
- Проверка роли `ADMIN` **в PostgreSQL на сервере** для страниц и API админки; скрытая кнопка сама по себе защитой не считается.
- Собственные изменяющие данные API проверяют точный `Origin` по `BETTER_AUTH_URL`. Запросы с чужим или отсутствующим Origin отклоняются.
- Для запросов к аккаунту и админке действует потоковый лимит **64 КБ JSON**, включая запросы без `Content-Length`; сервер проверяет тип `application/json`. Изменение цен, адресов и ролей через неподходящие поля не разрешено.
- У Better Auth явно включён rate limiting даже в `next dev`, с сохранением счётчиков в PostgreSQL. Чувствительные маршруты регистрации, входа и сброса пароля ограничены строже. Встроенные лимиты для TOTP сохраняются.
- HTTP-заголовки защищают от встраивания сайта в iframe, MIME sniffing, утечки URL через Referer, запуска объектов и подмены базового URL. Приватные страницы и API получают `Cache-Control: private, no-store`; `X-Powered-By` скрыт.
- HSTS включается **только для HTTPS** — локальный `http://localhost:3000` работает без него.

**Демонстрационный режим не меняется:** `CATALOG_SOURCE=demo`, каталог, тестовые заявки, предпросмотры и интерфейс продолжат работать как раньше.

## Применение изменений локально

Сначала остановить текущий `npm run dev` (`Ctrl+C`) в CMD из корня проекта:

```cmd
git pull --ff-only origin feature/storefront-catalog
npm run local:db:deploy
npm run local:check
npm run dev
```

Команда `local:db:deploy` применяет миграции только к изолированной локальной PostgreSQL и пересоздаёт Prisma Client. Она **не удаляет пользователей, сессии, заказы и Docker volumes**. Не запускать `migrate reset` или `docker compose down -v` на рабочей базе.

## Ограничение по IP и будущий продакшен

По умолчанию мы **не доверяем** `X-Forwarded-For`, который может подставить посетитель. Пока `PETROLERO_TRUSTED_IP_HEADER` не задан, входящие пользователи делят один лимит по IP на каждый маршрут. Этого достаточно для локальной разработки, но для публичного сайта нужно:

1. Поставить сайт за надёжный edge/reverse proxy, запретить прямые соединения с Next.js в обход него.
2. Настроить proxy так, чтобы он **перезаписывал**, а не дополнял, отдельный заголовок с реальным IP. Только после этого задать `PETROLERO_TRUSTED_IP_HEADER` (например, `cf-connecting-ip` на Cloudflare при правильной сетевой конфигурации). Не указывать произвольный `x-forwarded-for`, если посетитель может его подделать.
3. Включить HTTPS, production SMTP, секреты в защищённом хранилище переменных среды, резервные копии PostgreSQL и проверку восстановления.
4. Добавить защиту уровня инфраструктуры от DDoS и abuse (WAF/rate limits). Лимиты приложений не заменяют ограничения на edge.

## Второй этап: защита администратора и скриптов

- Административные страницы **и** все API требуют подтверждённый адрес, роль ADMIN и включённую TOTP-2FA. При отсутствии 2FA страницы перенаправляют на `/account/security`, а API отвечают HTTP 428. Пользователь может включить 2FA в кабинете без потери данных.
- Better Auth не выдаёт новую сессию на следующем входе с паролем, пока не подтверждён TOTP-код или резервный код.
- CSP ограничивает загружаемые скрипты собственным доменом, блокирует HTML-обработчики событий и не разрешает `unsafe-eval` в production. Inline-гидрация Next.js остаётся разрешённой, поэтому **это дополнительная защита, а не строгая XSS-изоляция**.
- В GitHub Actions выполняется `npm audit --omit=dev --audit-level=high`. По результатам аудита обновлены Next.js до 16.4.6, Nodemailer до 10.6.1, а уязвимые транзитивные пакеты Effect и Zod — до безопасных версий через `overrides`. Lockfile зафиксирован и проверен сборкой. Новые уязвимости будут блокировать CI.

## Что требует отдельного аудита до публикации

- Строгий nonce/hash-based `script-src` без `unsafe-inline`: Next.js Cache Components и существующие эффекты требуют отдельного тестирования, чтобы не нарушить гидрацию. Текущий CSP предотвращает сторонние скрипты, но не защищает от всех видов XSS.
- Управление и отзывом сессий, аудит зависимостей разработки, эксплуатационные проверки, защита edge и резервные копии.
- Проверка инфраструктуры, секретов, CSP и cookie-флагов после реального deployment, независимые тесты безопасности. Локальные интеграционные тесты не дают гарантии «сайт невозможно взломать».

## Тесты

CI выполняет миграции в **отдельную временную PostgreSQL** и проверяет роли и изоляцию пользователей, регистрацию и 2FA, блокировку слишком больших запросов и неправильного Content-Type, браузерные заголовки, Origin-CSRF, ограничения попыток входа при подделке `X-Forwarded-For`.

`scripts/check-security.mjs` намеренно вызывает множество неверных логинов; **не запускать на своей обычной локальной базе**, иначе временно сработает ограничение входа.
